## 把循环里的变量写成图的状态

现有循环的 `messages` 保存整段历史，`i` 表示已经到了第几次请求。拆成模型节点和工具节点后，这些信息要从一个节点交给下一个。`agent_graph.py` 已定义 `AgentState`，保存消息历史、已发出的模型请求次数、请求上限、可选输出上限和最终答案。审查时把 `message` 拼写改为 `messages`，与后续读写约定一致。初始请求次数为零，最终答案为 `None`。继续使用 Chat Completions 的消息字典，现有 `request_turn` 可以直接接收。

模型节点发一次请求，更新请求次数。得到文本后记录答案，得到工具请求后保存原来的 `assistant` 调用消息。图根据更新后的状态选择结束或执行工具。若最后一次仍要求调用工具，当场结束并沿用请求耗尽异常。工具节点从最新的 `assistant` 消息找到调用，执行后追加带同编号的 `tool` 消息，再回到模型节点。

`TypedDict` 描述一份普通字典有哪些键、每个值应是什么类型。它方便编辑器检查使用方式，真正的请求上限仍由应用在运行时校验。`build_initial_state` 已写入并通过静态检查。它去除问题两端的空白，检查请求次数上限，并用新的消息列表将计数初始化为零、答案初始化为 `None`。这份字典将来是图的输入。

下一步写模型节点 `model_node(state)`。它调用一次 `request_turn`，用 `parse_turn` 解释响应，将请求次数加一。`stop` 分支只需返回新计数和答案，工具请求分支返回新计数与追加了 `assistant` 消息的完整历史。首版要构造新列表，由框架用它替换旧字段。工具执行、回传和最后一次请求的分支判断在后续步骤接入。图版通过集中验收后，同一 CLI 入口切换到图版。

模型接口、工具实现和流程编排可以同写在一个文件里。这里拆开是为了让修改集中在有理由一起变化的代码。模型网络请求与响应解析留在 `model_client.py`，笔记查询留在 `tools.py`，状态和节点之间如何衔接放在 `agent_graph.py`。迁移期间可继续用 `agent.py` 中已验证的循环对照行为。

## 普通问答函数以后是否保留

状态类型、初始化和模型节点已写好并静态检查。模型节点的工具分支现在只追加 `assistant` 请求，工具结果由下一个节点负责。原始参数从 SDK 对象的 `call.function.arguments` 读取，保存到字典后，工具节点通过 `call["function"]["arguments"]` 取回同一个字符串。

`tool_node` 已写好。它从历史末尾取出模型请求，调用已有的 `execute_tool`，将结果放进带同一调用编号的 `tool` 消息，只返回更新后的 `messages`。静态审查确认请求次数仍由模型节点更新。

模型节点之后的路由已经写好。它先看是否已有答案，再看请求次数是否耗尽，最后才允许执行工具。三个分支标签是 `done`、`exhausted` 和 `tool`。接图时前两个指向结束点，后一个指向工具节点。`run_agent` 在图结束后将无答案的耗尽结果转成 `AgentRunError`，保持 CLI 的错误含义。

## 图已经连起来，并接入统一入口

使用项目解释器验证了一次完整路径。编译阶段未调用模型，传入初始状态后，第一次模拟响应请求查 RAG 笔记，本地工具执行并按原编号添加结果，第二次模拟响应给出答案。两次请求达到本次配置的上限，路由仍允许成功结束。检查确认历史由两条增长到四条，调用编号、笔记内容和最终答案正确。整个过程使用模拟模型响应和实际的本地笔记函数，没有发真实请求或新建测试文件。

`StateGraph` 负责收集节点名称、函数和连线。图执行时从 `START` 调度首个节点，每个节点返回对共享状态的更新，框架先合并这些更新，再按固定边或条件边安排下一节点。`compile()` 生成可执行的图，`invoke()` 才传入本次任务的数据并启动运行。下一步让 `run_agent` 调用已编译的图，继续给 CLI 返回文本或抛出原有异常。

`agent.py` 现在编译一次图，每次提问新建状态并调用 `invoke()`。最终状态有答案时返回字符串，耗尽时沿用 `AgentRunError`。CLI 继续使用同一个 `run_agent`。图的 `recursion_limit` 按模型请求上限计算，给模型节点和工具节点的执行留出余量。应用仍以 `max_model_calls` 决定能否继续请求模型。审查时移除了 `agent.py` 中原循环留下的导入，把返回类型改为 `str`。

统一入口集中模拟检查共七项通过，包含三项原有 CLI 测试和四项临时集成检查。连续提问的初始历史相互独立，工具调用两次后，第三次请求仍可返回答案。每条工具结果的编号及内容均和原请求对应。第三次请求若再次要求调用工具，程序只执行前两次，CLI 返回 1。未注册的工具也会提前停止，把错误送到标准错误流。检查使用实际 CLI、图和工具分发，模型响应使用替身。本轮没有新建测试文件或发真实模型请求。

`ask_once` 与旧演示已移除，原有用例按职责迁移。三项响应结构用例直接调用 `parse_turn`。鉴权、超时、连接失败、缺密钥和 token 参数传递由 `request_turn` 的用例覆盖。空白问题移入 CLI 测试，经过统一问答入口，确认程序没有尝试请求模型。

`append` 会直接改变调用者传入的列表，而 `state["messages"] + [assistant_message]` 会生成一个新列表。节点返回更新字典，框架据此替换 `messages` 字段。若以后给这个字段配置追加规则，节点也可以只返回新增消息，由框架负责合并。这比通过列表引用间接改变输入更容易定位每一步改了哪些数据。
